# Backend (FastAPI)

Owned by house-template-fastapi. Sources: the FastAPI docs (https://fastapi.tiangolo.com/), RFC 9457 (https://www.rfc-editor.org/rfc/rfc9457) and the pydantic-settings docs (https://docs.pydantic.dev/latest/concepts/pydantic_settings/).

- The import package is `app` under `backend/src/`; the app is built by `app.main.create_app`. Process-long resources (the database engine) open and close in `lifespan`, never at import time.
- Authentication: protect routes with `app.auth.CurrentUser` (or `OptionalUser`). Replace `app.auth.authenticate` with the project's real verification (session or bearer token, checked against the provider); until then production answers 401 everywhere, and `X-Dev-User` stands in for a user locally and in tests only. `User.id` is the provider's opaque subject, never an email; scope every owned row and query to it.
- API conventions: product routes live in `app/api/` and join `app.api.router` (mounted at `/v1`); a breaking change goes to a new `/v2` router beside it. Each route declares its return type (a Pydantic model, never an ORM object), protects itself with `CurrentUser`, and scopes queries to the user. List endpoints take `PageParamsDep` and return `Page[T]` built with `page()`: keyset (cursor) pagination, never offsets. `app/api/__init__.py` shows a whole resource.
- Dependencies use `Annotated[T, Depends(...)]` aliases. Settings come only from `app.settings.get_settings()` (tests pass a `Settings` to `create_app`); secrets are `SecretStr`, and every new setting goes in `backend/.env.example` with a safe value (a placeholder where there is no safe one).
- Errors are RFC 9457 problem details: raise `app.problems.Problem(status, detail=..., headers=...)` for expected failures (`Retry-After` on a 503 or 429). Never put submitted values, secrets or stack traces in an error body; unexpected errors are logged with the request id and return a bare 500.
- Every request logs one `request` line (method, route template, status, duration, request id), and library logs (uvicorn, SQLAlchemy) go through the same renderer, so production logs are JSON throughout. Log with `structlog.get_logger()` and keyword fields (`log.info("course_imported", course_id=...)`), never f-strings, and never log secrets or personal data.
- Readiness checks are registered with `app.health.add_readiness_check`; `/health/live` never touches a dependency.
- Production: the app refuses to start with `APP_ENV=production` on the local default database URL. Every connection has a statement timeout (30 s) and an idle-in-transaction timeout (60 s); commit or close a session before a long wait, and never hold a transaction across one. Migrations give up after waiting 5 s for a lock. CORS is off until `CORS_ORIGINS` lists the frontends; set `ALLOWED_HOSTS` in production. Responses carry nosniff, frame-deny, no-referrer and (unless a route sets its own) `Cache-Control: no-store`.
- Database: SQLAlchemy 2.1 async with psycopg 3. Inject `app.db.SessionDep`, commit explicitly, load relationships with `selectinload()` and declare them `lazy="raise"`. Models subclass `app.db.Base` and are imported in `app/models.py`.
- Migrations have two branches: the template's (`template`, arriving with template updates) and the project's (`app`). `make migration` writes on `app`; `make migrate` and the migrate job run `alembic upgrade heads`. Never give a project migration a template revision as its parent; use `depends_on` when it needs a template table.
- Every schema change is an Alembic migration (`make migration name="..."`), reviewed by hand: autogenerate misses renames, extensions and some constraints, and a migration says what happens to existing rows. `alembic check` runs in the tests, so a model without a migration fails `make check`. `make check` type-checks `migrations/` too; a plain `uv run mypy` reads only `src` and `tests` (`files` in `pyproject.toml`), so run it through make.
- Database tests use the `db_session` or `db_client` fixtures: a real PostgreSQL with pgvector (testcontainers, or `TEST_DATABASE_URL`), rolled back after each test. Never mock the database.
- Request bodies over `MAX_REQUEST_BYTES` (1 MiB) get a 413; large files must not come through the API.
- Tests are async (`pytestmark = pytest.mark.anyio`) and drive the app in-process through the `client` fixture; a bug fix comes with a test that fails without it.
- The image (`backend/Dockerfile`, `make image`; `make up` runs it with the database) installs the app from the lockfile into a virtualenv and runs it as UID 10001 with uvicorn, one process per container. On SIGTERM it finishes requests for `UVICORN_TIMEOUT_GRACEFUL_SHUTDOWN` (25 s): keep that under the platform's grace period. Set `FORWARDED_ALLOW_IPS` to the load balancer's addresses so client IPs and the scheme are right. Migrations never run at start-up: the `migrate` service locally, and a one-off job with the same image and `alembic upgrade heads` before each rollout. Deploy by the digest the publish workflow outputs, never a tag. Keep secrets out of the image (`.dockerignore`) and pass them as environment variables.
- Dependencies: add to `backend/pyproject.toml`, run `make lock`, commit both files. Optional parts are extras (`[project.optional-dependencies]`: `db` comes with the `database` answer, `langchain` with `llm: langchain`, `maf` with `llm: maf`, `storage` with the `storage` answer); `make install`, the make targets and the image install the ones this project answered for (`EXTRAS` in `mk/fastapi.mk`, `--extra` in the Dockerfile). To switch a part, commit first, then run `copier update --trust --defaults -a .copier-answers.fastapi.yml -d database=false` to turn the database off, `-d llm=langchain` to turn the model gateway on, or `-d storage=true` to turn storage on, then `make lock && make install && make check`. Turning the database off deletes the template's database files even if you edited them (`app/db.py`, `app/models.py`, `migrations/`, `compose/db/compose.yaml`, `tests/db.py`, the database tests; recover edits from git); your own files and `backend/uv.lock` stay. Tables are never dropped: to drop them, run `uv --directory backend run --locked --extra db alembic downgrade base` before updating, while Alembic and the migrations still exist. Your own migrations in `migrations/versions/` are left behind; `make check` still lints them with ruff but no longer type-checks them (Alembic is not installed): delete or move them. Your own code that imports `app.db` or `app.models` then fails `mypy`, and your own tests that use `db_session` or `db_client` fail in pytest. Remove `DATABASE_URL` from `backend/.env`; a running database container and the `db-data` volume are left behind (`docker compose down --remove-orphans`, then remove the volume). A database that ran without the model tables (migrations 0002 to 0008 did nothing there) gets them only after `copier update` has turned the model gateway on (stamping first would make `make migrate` re-run the empty revisions and leave no tables). Then, on every database the project runs against, production and staging included, and before the gateway is deployed, run `uv --directory backend run --locked --extra db --extra langchain alembic stamp 0001`, then `make migrate`; a new database needs only `make migrate`. FastAPI stays pinned to one minor (`<0.N+1`) because 0.x minors can break.
